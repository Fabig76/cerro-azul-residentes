## 2. Verificación del bug (empírica, no por lectura de código)

`submitRecord` en branch de **creación** llama `findRowByApto(apto)`; como
el apartamento ya existe, siempre rechaza.

```bash
# POST action=actualizarResidente, apto=218, cc=1128267275 (correcta), slot=1
# → {"ok":false,"error":"Ya existe un registro para el apartamento 218. ..."}
```

El flujo **"Editar mis datos"** del portal del residente (`residente.html`)
estaba **completamente roto**: ningún resident podía actualizar sus datos.

---

## 3. Hallazgo mayor: NO era solo `editMode`

Al construir el fix, se decidió **no** aplicar el parche mínimo de 1
línea a ciegas, sino escribir un **banco de pruebas** (harness) que
ejecutara el código real de `buildRowFromPayload` contra las **274 filas
reales** del Sheet y midiera exactamente qué celdas se perderían.

El banco de pruebas (Node + stubs de Apps Script) reveló que el bug de
fondo era **más grave**: el payload de `actualizarResidente` estaba
escrito **a mano** con 40+ campos y se había **desincronizado** de
`buildRowFromPayload`.

> ⚠️ **`registrarResidente` estaba destruyendo datos EN VIVO.** No era un

> residentes **borraba las autorizaciones legales, las emergencias, las
> mascotas y los vehículos del propietario**.

### 3.2 Causas raíz

1. **Falta `editMode: true`** (H-13) → el flujo siempre fallaba.
2. **Campos ausentes en el payload.** `buildRowFromPayload` hace
   `v[137] = d.autMenores ? 'Sí' : 'No'`. El payload mandaba `autDatos`
   pero **no** `autMenores` ni `autCom` → se escribía `'No'` y se
   **borraban** las autorizaciones legales del propietario.
3. **Claves desalineadas.** La función `validarYAplicarSlotsCompartidos`
   usaba nombres que `buildRowFromPayload` no leía:
   - `bicis`: usaba `tipo`/`rodado`; el backend lee `clase`/`serial`
   - `mascotas`: usaba `especie`/`edad`; el backend lee
     `tipo`/`nombre`/`raza`/`color`/`sexo`/`vacuna`/`manejoEspecial`/…
   - `contactos`: usaba `parentesco`/`celular`; el backend lee `parent`/`tel`
4. **Clave `emergencias` vs `contactos`.** `buildRowFromPayload` lee
   `d.emergencias`, no `d.contactos`. Con `contactos`, las columnas
   130-135 quedaban vacías.
5. **Tri-estados convertidos con truthiness.** `rowToObject` devuelve
   `'Sí'`/`'No'` como **string**, y `'No'` es *truthy* en JavaScript:
   `d.requiereRevision ? 'Sí' : 'No'` habría convertido **246 filas** a
   `'Sí'`.

---

## 4. La solución: `rowToObject`

`rowToObject(row.values)` **ya existía** en el codebase (línea 676) y hace
un round-trip fiel de las 143 columnas. En vez de mantener una lista
manual de 40+ campos que se puede desincronizar, el payload ahora se
construye así:

```javascript
const _base = rowToObject(row.values);          // round-trip fiel
const _aut  = _preservarAutorizaciones(row.values);

const payload = {
  ..._base,                                      // todo lo del propietario
  editMode: true,                                // BUGFIX-027 (H-13)
  // ...solo se sobreescribe lo que el resident puede cambiar
};
```

**Por construcción es imposible perder un campo**: si no está en la
sobreescritura, viene del Sheet.

### 4.1 Funciones auxiliares agregadas (8)

| Función | Propósito |
|---|---|
| `_preservarTriEstado(v)` | `'Sí'`→`true`, `'No'`→`false`, `''`→`''` (para `requiereRevision` y `manejoEspecial`) |
| `_preservarAutorizaciones(values)` | Cols 136/137/138 como booleanos (no strings truthy) |
| `_preservarDispositivos(values)` | Cols 95-109 con claves canónicas |
| `_preservarSlotCompartido(values, tipo, base, ancho, num)` | Reconstruye un slot compartido desde el Sheet con las claves que lee `buildRowFromPayload` |
| `_slotVacio(tipo)` | Objeto vacío con las claves canónicas del tipo |
| `_normalizarNuevoSlot(tipo, obj)` | Traduce las claves del frontend del residente (`js/residente.js`) a las canónicas |
| `_combinarSlotsCompartidos(...)` | Slot con datos → gana el Sheet. Slot vacío → entra el dato del resident |
| `_combinarMenores(values, nuevos)` | Preserva menores del Sheet; usa los del resident solo si el slot está vacío |

### 4.2 `_combinarSlotsCompartidos` — la regla de negocio

Regla de `docs/spec-residente.md` §22.7: *"Editar/agregar vehículo/mascota/
bici/contacto a slot vacío → Residente con CC"* y *"Modificar slot ocupado
por OTRO residente → ❌ (solo propietario/admin)"*.

```
slot con datos en el Sheet  -> se preserva intacto (gana el Sheet)
slot vacío + dato del res.  -> entra el dato del resident
slot vacío + sin dato       -> queda vacío
```

**Bug encontrado por el banco de pruebas:** la primera versión asignaba el
dato del resident al slot del **mismo índice**. Si el propietario tenía V1
ocupado y el resident traía un vehículo, el vehículo **se descartaba**.
Corregido: los datos del resident van al **primer slot vacío**
(`siguiente` counter), nunca al del mismo índice.

## 9. Lección aprendida

**No aplicar un parche mínimo de 1 línea sin medir el alcance real.**

El fix de 1 línea (`editMode: true`) habría "arreglado" el flujo del
resident y, al mismo tiempo, **activado la destrucción de 1.585 celdas**
en 200 registros — incluyendo 242 autorizaciones legales de comunicaciones
y 192 de datos de menores. El bug se llevaba a cuestas.

El banco de pruebas (ejecutar el código real contra las filas reales del
Sheet) es lo que convirtió "1 línea" en "reconstrucción fiel con
`rowToObject` + 8 auxiliares + 3 tests E2E nuevos".

**Regla generalizable:** cuando un fix "mínimo" habilite un flujo que
llevaba tiempo fallando, hay que auditar **qué hace ese flujo cuando
funciona** antes de habilitarlo. El fallo puede haber estado enmascarando
destrucción de datos.
