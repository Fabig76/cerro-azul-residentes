## BUGFIX-005 / BUGFIX-012 — `registrarResidente` cae al branch de CREACIÓN de `submitRecord`

### Síntoma
Residente del apto 1108 (CA-0133, propietario Luisa María) intenta auto-registrarse vía `residente.html` → ve error del **formulario principal** (`index.html`) en lugar de un mensaje del portal residente.

### Causa raíz
`apps-script/Código.gs` `registrarResidente(data)` (líneas 1989-2079) construía un payload compatible con `submitRecord()` pero **omitía `editMode: true`**. `submitRecord` entraba al branch de CREACIÓN, ejecutaba `findRowByApto(apto)`, encontraba CA-0133 (creado por el propietario), y retornaba el error "Ya existe un registro..." en línea 255.

### 3 side effects adicionales descubiertos
1. `autDatos: true` hardcoded (línea 2059) → sobrescribía el checkbox de autorización del propietario
2. `dispositivos: []` hardcoded (línea 2055) → borraba cualquier llavero/tag autorizado por el propietario
3. Mensajes del formulario principal llegaban al portal residente sin filtro

### Fix (5 partes en `Codigo.gs`)
1. `editMode: true` en el payload (CLAVE)
2. `autDatos` preserva el original del propietario (`String(row.values[136] || '') === 'Sí'`)
3. FIX REAL `dispositivos` — copia los originales del propietario desde cols 95-109 (porque `setValues([row])` escribe las 143 columnas completas, no parcial)
4. Mensaje de error "ya hay residentes" reescrito sin referencia al `index.html`
5. Sanitización de errores de `submitRecord` (regex `/EDITAR MI REGISTRO/` → mensaje genérico)

## BUGFIX-006 / BUGFIX-013 — Parentesco del residente se pierde (mismatch `parentesco`/`parent`)

### Síntoma
Durante T-V21-4b, `verificarResidente` retorna:
```json
{"slot":1,"datos":{"nombre":"TEST BUGFIX012","cc":"99999991","parentesco":"","cel":"3000000001","correo":"test-bugfix012@test.co"}}
```

El residente envió `parentesco: 'Tenedor / Otro'` desde `residente.js` pero el Sheet guardó col 33 vacía.

### Causa raíz
Desajuste de nombres entre el frontend y el backend:
- `js/residente.js` línea 466 envía `parentesco`
- `apps-script/Código.gs` línea 336 (`buildRowFromPayload`) lee `r.parent`

`buildRowFromPayload` busca `r.parent` y recibe `undefined` → escribe string vacío en col 33.

**Bug preexistente desde V13 (25-Sept-2026) — NO introducido por V21.** Descubierto durante testing de V21.

### Fix (14 líneas en `registrarResidente`)
```javascript
// BUGFIX-013: buildRowFromPayload lee `r.parent` para escribir v[33], pero
// residente.js envía `r.parentesco`. Sin normalización, col 33 queda VACÍA.
const residentesCrudos = Array.isArray(data.residentes) ? data.residentes : [];
const residentes = residentesCrudos.map(function (r) {
  return {
    nombre: r.nombre || '',
    cc: r.cc || '',
    correo: r.correo || '',
    cel: r.cel || '',
    parent: r.parentesco || r.parent || ''   // <-- FIX: acepta ambos
  };
});
```

El normalizador acepta tanto `r.parentesco` (portal residente) como `r.parent` (compatibilidad con `index.html`). **No-op para el formulario principal.**

## Lecciones aprendidas (#4, #5, #6, #7 de la sesión, además de #12 y #13)

### #4 — Verificar estado del Sheet antes de tocar
Antes de cualquier operación destructiva sobre el Sheet (`clearResidente`, `submitRecord` con auto-creación, etc.), **siempre** verificar el estado actual con `getEstadoResidente` o equivalente. **Confirmar con el operador ANTES de ejecutar.**

### #5 — Backup pre-clear
Cuando se hace `clearResidente`, hacer backup del Sheet completo exportando a XLSX. Subirlo a Drive carpeta del proyecto. **No confiar solo en la reversibilidad teórica.**

### #6 — Comunicación proactiva de operaciones destructivas
Cuando una operación puede borrar >0 celdas, **avisar al operador antes**. No después. La excepción "es solo el sentinel" no aplica si el operador ha interactuado con ese sentinel desde la última sesión.

### #7 — Cold start de Apps Script Web App post-deploy
La primera llamada a un Apps Script Web App después de un deploy tarda 30-60 segundos (cold start). El navegador aborta a los 30s con "Failed to fetch" o retorna HTML. **Mitigación documentada en GUIA-PROYECTO §16:** operador abre la URL manualmente una vez tras deploy para que warm cache antes de que los residentes prueben.
